# AIソロTRPG型ゲームブックサービス

## 1. サービス概要

このサービスは、AIがTRPG風のゲームブックを生成し、一人でも物語を楽しめるWebサービスです。

ゲームブックの手軽さとTRPGの没入感を組み合わせ、遊ぶ仲間やゲームマスターがいないときでも、自分の好きなタイミングで冒険を始められる体験を提供します。

TRPGを遊びたいものの、参加者との予定調整やゲームマスターの不在によって遊べない人の課題を、AIによるゲームブック生成とWeb上での選択式プレイによって解決します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

私はTRPGが好きで、実際にプレイヤーとして遊んだり、ゲームマスターを担当したりした経験があります。

しかし、TRPGは複数人で遊ぶことが多く、参加者同士で予定を合わせる必要があります。

そのため、「今日遊びたい」「今から少しだけ遊びたい」と思っても、一緒に遊ぶ人が集まらず、すぐに遊べないことが何度もありました。

ゲームブックであれば一人で遊べますが、あらかじめ用意された選択肢の中から行動を選ぶことが中心となるため、TRPGのような探索感や、自分の選択によって物語が変化する感覚がもう少し欲しいと感じることもありました。

AIによる文章生成を利用すれば、ユーザーが入力したジャンルや世界観に合わせて、毎回異なる物語や分岐を作れるのではないかと考えたことが、このサービスを思いついたきっかけです。

---

### 2-2. なぜそれが「気になった」のか

私は、何かを遊びたいと思ったときに、なるべくその気持ちがあるうちに始めたいと考えています。

しかし、遊ぶために長い準備や日程調整が必要になると、その間に遊びたいという気持ちが薄れてしまうことがあります。

また、TRPGのように、自分の選択や判断によって物語が変化する遊びが好きです。

そのため、誰かが集まるのを待たなくても、一人で物語に入り込み、自分の選択によって展開が変わる体験を気軽に楽しめる環境があれば、自分自身も利用したいと考えました。

---

## 3. 課題の整理

### 3-1. 表に見えている困りごと

TRPGを遊びたいと思っても、一緒に遊ぶ参加者やゲームマスターが集まらず、自分の好きなタイミングで遊べないことです。

---

### 3-2. 本当に解決したい課題は何か

#### なぜ1

なぜTRPGをすぐに遊べないのか。

参加者同士で日程を調整し、複数人が同じ時間に集まる必要があるためです。

#### なぜ2

なぜ複数人が集まらないと遊べないことが困るのか。

自分が遊びたいと思ったタイミングと、他の参加者が遊べるタイミングが一致するとは限らないためです。

#### なぜ3

なぜ遊びたいタイミングを逃すことが問題なのか。

遊びたいという気持ちがあるうちに体験できず、結果としてTRPGに興味があっても、実際に遊ぶ機会が少なくなってしまうためです。

### 本当に解決したい課題

TRPGを遊びたいと思った人が、他の参加者の予定やゲームマスターの有無に左右されず、一人でもすぐに物語を楽しめる環境がないことです。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

#### 年齢設定

* 年齢：20代後半
* 理由：TRPG配信、リプレイ動画、ゲーム実況などをきっかけにTRPGへ興味を持ちやすく、Webサービスや生成AIを使うことへの抵抗も比較的少ないと考えているためです。

幅広い年代を対象にするのではなく、最初は以下のような一人を想定しています。

> 仕事が終わった夜や休日にゲームを遊んでいる20代後半の一人暮らしの人。
> TRPGの配信やリプレイ動画を見ることが好きで、数回遊んだ経験もある。
> しかし、定期的に遊ぶグループには所属しておらず、遊びたいと思った日に参加者を集めることが難しい。

#### 生活・状況設定

* 生活・状況：平日は仕事があり、夜や休日に30分から1時間程度ゲームを遊んでいる
* 理由：まとまった時間や事前の予定調整が必要なTRPGは遊びにくい一方で、一人で短時間から始められるサービスであれば利用しやすいためです。

このサービスでは、ユーザーがジャンルや世界観などを入力するだけでゲームブックを生成し、生成後は自分のペースで遊べるようにします。

#### 環境設定

* 環境：パソコンやスマートフォンからWebサービスを利用できる
* 理由：専用アプリやルールブックを準備しなくても、ブラウザからすぐに始められるようにすることで、利用開始までのハードルを下げられるためです。

## 8. このアプリの懸念点とその対策

### 懸念点①：AI APIの運用コスト

#### 何が問題になりそうか

プレイヤーの行動や選択のたびにAIへ問い合わせる仕組みにすると、利用者数やプレイ時間に比例してAPIの利用料金が増加する可能性があります。

また、生成のやり直しや不正な大量アクセスによって、想定以上の費用が発生する可能性があります。

#### なぜそう思うか

AI APIは、送信する文章量と生成される文章量に応じて料金が発生します。

プレイ中の履歴を毎回送信する場合、ゲームが進むほど送信する情報量が増え、1回あたりの料金も高くなる可能性があります。

#### そのために考えている対策

MVPでは、ゲーム開始前にAIが物語、シーン、選択肢、分岐、エンディングをまとめて生成します。

プレイ中は原則としてAIを呼び出さず、以下の処理をRuby on Railsとデータベースで行います。

* シーン遷移
* 選択肢の表示
* フラグ更新
* 所持品管理
* ダイス判定
* エンディング判定
* セーブとロード

また、以下の利用制限も検討します。

* 1ユーザーあたりの1日の生成回数を制限する
* 入力可能な文字数を制限する
* AIが生成する文章量に上限を設定する
* 生成中は新しい生成を開始できないようにする
* APIエラー時の自動再試行回数を制限する
* ユーザーごとの生成回数を記録する
* 管理画面でAPI利用状況を確認できるようにする
* 月間予算に達した場合は生成を停止する

---

### 懸念点②：AIが生成した分岐に矛盾が発生する可能性

#### 何が問題になりそうか

AIが生成したシーン同士のつながりに矛盾があったり、取得していないアイテムを使用できたり、到達できないシーンが生成されたりする可能性があります。

#### なぜそう思うか

文章として自然に見えても、分岐構造やフラグ条件がゲームとして正しく成立しているとは限らないためです。

#### そのために考えている対策

AIから自由な文章だけを受け取るのではなく、以下のような構造化されたデータとして受け取ります。

* シーン番号
* シーン本文
* 選択肢
* 遷移先
* 必要なフラグ
* 追加するフラグ
* 必要な所持品
* 取得できる所持品
* エンディング種別

生成後にアプリ側でデータを検証し、存在しないシーンへの遷移や不正な参照がある場合は、保存前にエラーとして扱う仕組みを検討します。

---

### 懸念点③：AIが生成した物語の品質にばらつきが出る可能性

#### 何が問題になりそうか

物語が単調になる、選択肢による違いが少ない、文章が長すぎる、結末が不自然になるなど、生成結果の品質にばらつきが出る可能性があります。

#### なぜそう思うか

生成AIは同じ条件でも毎回異なる結果を返すため、すべての作品が同じ品質になるとは限らないためです。

#### そのために考えている対策

* シーン数や文章量を指定する
* 各シーンの役割を明確にする
* 選択肢ごとに異なる結果を設定する
* エンディング数を固定する
* AIへの指示文を改善する
* 生成結果の評価機能を追加する
* プレイ後の感想をもとに改善する
* 不適切な生成結果を報告できるようにする

### 10-2. 技術選定の比較検討

| 候補                   | 採用・不採用   | 理由                                                                  |
| -------------------- | -------- | ------------------------------------------------------------------- |
| Ruby on Rails        | 採用       | これまでの学習経験を活かし、認証、データベース操作、画面表示などを一つのフレームワークで実装できるため                 |
| Next.js              | 不採用      | 動的な画面を作りやすい一方で、新しく学ぶ範囲が広く、MVP完成までの期間が長くなる可能性があるため                   |
| React                | MVPでは不採用 | プレイ画面との相性は良いと考えられるが、まずはRuby on RailsとStimulusで完成させ、本リリース後に導入を検討するため |
| PostgreSQL           | 採用       | Ruby on Railsとの相性がよく、シーン、選択肢、プレイ状況、フラグなど複数の関連データを管理しやすいため           |
| MySQL                | 不採用      | 使用可能ではあるが、現在の開発環境とデプロイ環境でPostgreSQLを利用しているため                        |
| OpenAI Responses API | 採用       | 構造化された形式でシーン、選択肢、分岐、エンディングなどを生成できるため                                |
| 他の生成AI API           | MVPでは不採用 | 複数サービスへ同時対応すると実装と検証の範囲が広がるため、最初は一つのAPIに絞る                           |
| Render               | 採用       | Ruby on RailsアプリとPostgreSQLをデプロイした経験があり、既存の知識を活かせるため                |
| AWS                  | 不採用      | 高い拡張性がある一方で、MVP段階では設定や運用の学習コストが大きいため                                |
| Bootstrap            | 採用       | 既製のコンポーネントで短期間に画面を作成できるが、今回はゲームブック独自の世界観に合わせたデザイン調整を優先するため                                 |
| Tailwind CSS         | 採用      | ユーティリティクラスを組み合わせて、ゲームブックの世界観に合わせた画面を柔軟に作成しやすいため                         |
| Hotwire・Stimulus     | 採用       | Ruby on Railsとの相性がよく、生成状況の確認やプレイ画面の一部更新を、Reactを導入せずに実装できるため         |

---

### 今回チャレンジしたい点

* AIからゲームブックを構造化データとして受け取ること
* 生成したシーンと選択肢をデータベースへ保存すること
* 複数のシーンを分岐で関連付けること
* フラグや所持品によって選択肢を変化させること
* プレイヤーごとの進行状況を管理すること
* AI APIの利用料金を意識した設計を行うこと
* AIを常時利用せず、Webアプリ側の処理と組み合わせること
* ゲームとして分かりやすい画面を作ること

---

### 不安な点

* AIが正しい分岐構造を生成できるか
* AIが生成したデータをどのように検証するか
* シーンやフラグの設計が複雑になりすぎないか
* 生成した物語がゲームとして面白くなるか
* OpenAI APIの利用料金を抑えられるか
* 生成処理に時間がかかった場合の画面設計
* Issueごとの作業量を正確に見積もれるか
* MVPの機能範囲が広くなりすぎないか

---

### 10-3. キャッチアップ不足の懸念

新しく使用する技術や実装方法について、理解が不足した状態で開発を始めると、以下の問題が発生する可能性があります。

#### 1. 完成までのハードルが高くなる

使用経験が少ない技術を多く採用すると、機能実装だけでなく、技術自体の学習にも時間が必要になります。

そのため、MVPではこれまで学習してきたRuby on Railsを中心に実装します。新しく採用するOpenAI Responses API、Tailwind CSS、ゲーム進行管理については、それぞれの導入目的を明確にし、必要な範囲に絞って使用します。

#### 2. Issueの見積もりが難しくなる

理解している部分と分からない部分が整理されていない場合、調査や実装にどれくらい時間がかかるかを判断しにくくなります。

そのため、大きな機能をそのまま一つのIssueにせず、以下のように小さく分割します。

* ゲームブック生成フォームを作成する
* AI APIへ生成条件を送信する
* 構造化された生成結果を受け取る
* ゲームブックを保存する
* シーンを保存する
* 選択肢を保存する
* 最初のシーンを表示する
* 選択肢から次のシーンへ移動する
* プレイ状況を保存する
* フラグを更新する
* エンディングを表示する

Reactについては、MVP段階では導入せず、本リリース後に単体でキャッチアップを行います。

その後、プレイ画面の操作性や演出を改善するために必要かを技術検証し、導入するか判断します。

---

## 11. ゲーム体験の設計

この企画では、AIによる物語生成だけでなく、生成された内容をゲームとしてどのように遊ぶかが重要になります。

そのため、MVPの実装前に、以下のゲーム体験について具体的に整理します。

---

### 11-1. ゲームはどのような単位で進むか

MVPでは、ゲームを「シーン単位」で進行させる予定です。

各シーンには、以下の情報を持たせます。

* シーンタイトル
* シーン本文
* 現在の状況
* プレイヤーが選べる選択肢
* 選択後の移動先
* 必要なフラグ
* 追加または削除するフラグ
* 必要な所持品
* 取得または消費する所持品
* エンディングかどうか

#### シーン制を採用する理由

ページ番号を選んで移動する従来のゲームブック形式ではなく、Web画面上で一つの場面を一つのシーンとして表示します。

シーン単位にすることで、以下の処理を実装しやすくなります。

* 選択肢をボタンとして表示する
* 選択した結果に応じて次のシーンへ移動する
* フラグや所持品を更新する
* プレイ状況を保存する
* 条件を満たした場合のみ選択肢を表示する
* エンディングへの到達を判定する

---

### 11-2. 1シーンに表示する選択肢の数

MVPでは、1シーンにつき2個から4個程度の選択肢を表示する予定です。

選択肢が1個だけの場合、ユーザーが自分で物語を選んでいる感覚が弱くなります。

一方で、選択肢が多すぎると、それぞれの分岐やシーンを管理する負担が大きくなり、AIが生成する物語にも矛盾が発生しやすくなります。

そのため、基本は3個程度とし、場面に応じて2個から4個の範囲に収めます。

例：

* 周囲を調べる
* NPCに話しかける
* 次の部屋へ進む

すべての選択肢が完全に別の物語へ分岐するのではなく、一部は異なる情報やアイテムを取得したあとに、共通のシーンへ戻る構成も利用します。

これにより、ユーザーの選択による変化を残しながら、必要なシーン数が増えすぎることを防ぎます。

---

### 11-3. フラグによる分岐の管理

プレイヤーの行動結果は、フラグとしてデータベースへ保存します。

フラグとは、「どのような行動をしたか」「どの情報を知っているか」などを表す状態です。

例：

* NPCを助けた
* 鍵を入手した
* 隠し部屋を発見した
* 怪しい人物の正体を知った
* 特定のイベントを見た

フラグによって、後のシーンで表示される文章や選択肢を変化させます。

例：

```text
「鍵を入手した」フラグがある
→ 鍵を使って扉を開ける選択肢を表示する

「NPCを助けた」フラグがある
→ 終盤でNPCが助けに来る

「真相を知った」フラグがある
→ トゥルーエンディングへ進める
```

MVPでは複雑な数値計算を避け、フラグが存在するかどうかを中心に管理します。

---

### 11-4. 1プレイのボリューム

MVPでは、1プレイ30分程度を想定します。

長すぎるゲームブックを生成すると、AIの生成料金が高くなり、物語全体の矛盾も発生しやすくなります。

一方で、短すぎる場合はTRPGらしい探索や選択を体験しにくくなります。

そのため、最初は以下のボリュームを目安にします。

* 想定プレイ時間：30分程度
* 1回のプレイで通過するシーン数：8から12シーン程度
* ゲーム全体のシーン数：15から25シーン程度
* 1シーンの選択肢：2から4個
* エンディング数：3個程度

---

### 11-5. シーンの構成

MVPでは、物語全体を以下のような役割のシーンで構成する予定です。

#### 1. 導入シーン

* 主人公が置かれている状況を説明する
* 目的を提示する
* 最初の選択肢を表示する

#### 2. 探索シーン

* 場所を調べる
* NPCと出会う
* 手がかりや所持品を取得する
* 複数の行動から選択する

#### 3. 状況変化シーン

* 新しい事件が発生する
* 敵や危険が現れる
* 制限時間や新しい目的が提示される

#### 4. 情報整理シーン

* 取得した手がかりを確認する
* 真相を推理する
* 次に進む場所を選択する

#### 5. クライマックスシーン

* 重要な選択を行う
* 判定に挑戦する
* これまでのフラグや所持品が結果へ影響する

#### 6. エンディングシーン

* プレイヤーの選択結果を表示する
* 到達したエンディング名を表示する
* 最初から遊び直すか、一覧へ戻るかを選択する

---

### 11-6. エンディング数

MVPでは、3種類程度のエンディングを用意する予定です。

例：

* バッドエンディング
* ノーマルエンディング
* トゥルーエンディング

#### バッドエンディング

危険な選択をした場合や、必要な情報を集められなかった場合に到達します。

#### ノーマルエンディング

物語の目的は達成したものの、すべての真相や問題を解決できなかった場合に到達します。

#### トゥルーエンディング

特定の手がかり、所持品、フラグなどを集めたうえで、正しい選択をした場合に到達します。

複数のエンディングを用意することで、一度クリアしたユーザーが別の選択肢を試す理由を作ります。

---

### 11-7. TRPGらしさをどこまで入れるか

MVPでは、TRPGのすべての要素を実装するのではなく、ゲームブックとして遊びやすく、実装可能な範囲に絞ります。

#### MVPで取り入れる予定の要素

* 選択による物語の変化
* 探索
* 手がかり
* 所持品
* フラグ
* 複数のエンディング
* 簡単なダイス判定
* NPCとの選択式会話

#### 本リリース以降に検討する要素

* HP
* 攻撃力などの能力値
* キャラクター作成
* スキル
* 戦闘
* キャラクター成長
* NPCとの自由会話
* プレイヤーによる自由入力
* AIによるゲームマスターとしての裁定

---

### 11-8. ダイス判定

ダイス判定は、MVPで実装するかを検討中です。

実装する場合は、複雑なTRPGルールを採用せず、Webアプリ側で完結する簡単な判定にします。

例：

```text
1D6を振る

4以上
→ 成功シーンへ進む

3以下
→ 失敗シーンへ進む
```

または、所持品やフラグによって成功しやすくします。

例：

```text
「ロープ」を持っている
→ 判定にプラス1

「負傷している」フラグがある
→ 判定にマイナス1
```

ダイスの結果はRuby on Rails側で処理し、AI APIは使用しません。

---

### 11-9. 所持品

プレイヤーは探索中に所持品を取得できます。

例：

* 鍵
* 懐中電灯
* 地図
* 薬
* 手紙
* 武器
* 記録媒体

所持品は、特定の選択肢を表示したり、判定を有利にしたり、エンディング条件として利用します。

所持品を増やしすぎると管理が複雑になるため、MVPでは1作品につき3個から5個程度を目安にします。

---

### 11-10. HP

MVPでは、HPを実装しない方向で検討しています。

HPを導入すると、ダメージ、回復、ゲームオーバー、戦闘バランスなど、追加で検討する項目が増えるためです。

MVPでは、危険な選択の結果をシーン遷移やフラグで表現します。

例：

```text
危険な選択をする
→ 「負傷した」フラグを追加する

「負傷した」フラグがある
→ 後の判定が不利になる
```

本リリースでは、戦闘やキャラクター成長を追加する場合に、HPの導入を再検討します。

---

### 11-11. ステータス

MVPでは、複数の能力値やレベルなどの本格的なステータスは実装しない予定です。

最初から能力値を増やすと、AIがシナリオを生成する際に、判定難易度やゲームバランスまで考慮する必要があるためです。

MVPでは、以下のような単純な状態管理を中心にします。

* 所持品
* フラグ
* 到達したシーン
* 現在のシーン
* ダイス判定の結果
* 到達したエンディング

本リリース後にキャラクター作成を追加する場合は、以下のような能力値を検討します。

* 体力
* 知力
* 器用さ
* 精神力

---

### 11-12. NPCとの会話

MVPでは、NPCとの会話は自由入力ではなく、選択式にします。

例：

```text
NPCに何を聞きますか？

- この建物について聞く
- 失踪事件について聞く
- 持っている鍵について聞く
```

選択した内容に応じて、NPCの返答が表示されます。

また、特定のフラグや所持品を持っている場合のみ表示される会話も用意します。

例：

```text
「古い写真」を持っている
→ 「この写真を見せる」という選択肢を表示する
```

自由入力による会話は、API利用料金と物語の整合性の管理が難しいため、本リリース以降の機能として検討します。

---

### 11-13. MVP時点でのゲーム体験

MVP時点では、以下の流れで遊べる状態を目指します。

```text
生成条件を入力する
↓
AIがゲームブック全体を生成する
↓
生成結果をデータベースへ保存する
↓
最初のシーンからゲームを開始する
↓
文章を読んで選択肢を選ぶ
↓
フラグや所持品が更新される
↓
次のシーンへ移動する
↓
必要に応じて簡単なダイス判定を行う
↓
これまでの選択に応じたエンディングへ到達する
↓
結果を確認する
```

この構成により、ゲームブックの分かりやすさを保ちながら、探索、所持品、判定、フラグ、複数エンディングといったTRPGらしい要素を取り入れます。

---

## 12. MVPで検証したいこと

MVPでは、多くの機能を実装することだけを目的とせず、このサービスに需要があるか、ゲームとして楽しめるかを検証します。

### 検証したい内容

* ユーザーは、自分の好みに合わせたゲームブックを生成したいと思うか
* AIによって生成された物語を最後まで遊んでもらえるか
* 選択肢による進行だけでもTRPGらしさを感じられるか
* 30分程度のプレイ時間が適切か
* 1シーンあたり2個から4個の選択肢が遊びやすいか
* 所持品やフラグによる変化が楽しさにつながるか
* 複数のエンディングが再プレイの理由になるか
* 自由入力がなくてもサービスとして価値を感じてもらえるか
* 1作品あたりのAI API利用料金を現実的な範囲に抑えられるか
* AIが生成したシーンや分岐がゲームとして成立するか

### 検証方法

* 知人やTRPG経験者に実際にプレイしてもらう
* プレイ後に感想を聞く
* 分かりにくかった画面や選択肢を確認する
* ゲームを最後まで遊んだか確認する
* もう一度遊びたいと思ったか確認する
* 自由入力が欲しいと感じたか確認する
* 生成時間とAPI利用料金を記録する
* 到達したエンディングや途中離脱したシーンを記録する

---

## 13. 現時点でのMVP方針

現時点では、以下の方針でMVPを作成します。

* AIが事前にゲームブック全体を生成する
* プレイ中は原則としてAI APIを利用しない
* ゲームはシーン単位で進行する
* 1シーンにつき2個から4個の選択肢を表示する
* 1プレイ30分程度を想定する
* 1回のプレイで8から12シーン程度を通過する
* ゲーム全体では15から25シーン程度を生成する
* エンディングは3種類程度用意する
* フラグと所持品によって分岐を変化させる
* NPCとの会話は選択式にする
* HPや複雑な能力値はMVPでは実装しない
* ダイス判定は簡単な形式での導入を検討する
* 自由入力やAIによるリアルタイム進行は本リリース以降に検討する

まずは、AIが生成したソロTRPG型ゲームブックを、ユーザーが迷わず最後まで遊べる状態を目指します。
